# 项目上下文

> 状态：已确认

## 项目定位

- 当前仓库是 ESP32-C3 的独立工牌展示固件。工牌首页、设置页、按需 SoftAP/HTTP 配置网页、工牌资料双槽事务存储已经实现。
- `specs/20260927_badge_personalization_ui_enhancement/` 已完成并关闭：工牌页使用完整 240×320 页面；个性化模式保留稳定 ID，但因没有内容而被导航跳过；Wi-Fi 配置网页已经支持工牌照片、姓名和自定义语句。
- 本规格新增真正的“个性化”图片页和对应网页配置，不重新设计已经验收的工牌资料格式、工牌上传协议、热点生命周期或设置交互。
- 当前工作区已有用户的暂存改动。本规格 Phase 0～3 只修改本目录，后续实现必须保留所有无关改动。

## 技术栈与构建

- 硬件：ESP32-C3、8 MB Flash、无 PSRAM、240×320 ST7789、ADC 三按键。
- SDK：ESP-IDF 5.5.3，由 PlatformIO `platformio/espressif32@6.13.0` 驱动。
- UI：LVGL 9、`esp_lvgl_port`、全屏 240×320 公共内容容器。
- 网络：ESP-IDF SoftAP、DHCP、HTTP Server；手机连接热点后访问 `http://192.168.4.1/`。
- Web：固件内嵌离线 HTML/CSS/原生 JavaScript；浏览器负责图片解码、裁剪、拖动、缩放、旋转及 RGB565 LE 转换。
- 存储：工牌资料位于 `badge_data@0x310000/0x40000`；设备身份位于 `cardid@0x356000/0x4000`；普通上传不得擦除 NVS、`badge_data` 或 `cardid`。
- 自动化：PlatformIO native + Unity 覆盖纯 C 逻辑，Node 测试覆盖 Web 图片和协议逻辑，目标构建使用 `pio run`。

## 当前相关架构

### 设备导航与个性化占位

- `mode_registry_t.business` 注册工牌和个性化两个稳定模式；长按上/下在可用业务模式之间切换，长按确认进入设置。
- `mode_t::is_available` 已提供通用可用性判断。`custom_mode_t.has_content` 当前固定为 false，所以个性化页不会进入业务循环。
- 短按按键会交给活动模式的 `handle_key`，当前个性化模式尚未实现本地按键行为，可用于在已保存图片之间切换而不改变全局长按语义。
- `custom_view` 当前只创建空白全屏页面；没有图片描述符、槽位状态或刷新逻辑。

### 现有工牌配置链路

- 设置页主动开启热点，浏览器访问固定地址。HTTP 会话 token、单次写事务、分块接收、上传期间 Busy 和按键安全退出均已实现。
- 现有页面默认展示工牌配置表单。浏览器使用 Canvas 完成图片 cover 裁剪、拖动、1～4 倍缩放、90° 旋转和 RGB565 LE 转换。
- `GET /api/profile`、`GET /api/photo`、`POST /api/profile` 和工牌 version 2 envelope 已稳定使用；新增个性化配置不得改变这些端点及其语义。
- `badge_image.js` 的图片解码、旋转、RGB565 编解码可以复用，但现有裁剪几何和遮罩逻辑以 200×200 方形输出为中心，需要扩展为矩形输出且保证工牌行为不变。
- `badge_http_server` 当前同时承担离线资源、状态、工牌读取和工牌上传路由；运行时 URI handler 数量为 8，新增接口需要调整路由组织或上限。

### 现有持久化模式

- `badge_store` 使用两个 `0x20000` 物理槽保存一个逻辑工牌资料：先擦除非活动槽、流式写入、读回 CRC 校验，最后写提交标记。
- `badge_partition` 将数据分区 mmap，LVGL 图片描述符直接引用映射后的 Flash 像素，不为完整图片额外申请堆内存。
- 工牌图片为 200×200 RGB565 LE，共 80,000 字节。个性化图片若与屏幕原生像素一一对应，则为 240×320 RGB565 LE，共 153,600 字节。

## 三槽容量评估

### 原始容量

| 项目 | 计算 | 结果 |
| --- | --- | ---: |
| 单张全屏图片 | 240 × 320 × 2 字节 | 153,600 B |
| 三张有效图片 | 153,600 × 3 | 460,800 B |
| 每槽双副本事务存储 | 3 × 2 × `0x28000` | 983,040 B |
| 建议新分区 | `custom_data@0x35A000/0x100000` | 1,048,576 B |
| 分区内预留 | 1,048,576 - 983,040 | 65,536 B |

- 当前分区表在 `cardid` 结束地址 `0x35A000` 之后，到 8 MB Flash 末尾仍有 4,874,240 字节未分配空间。
- 为每个逻辑槽位分配两个 `0x28000` 物理记录，可容纳 153,600 字节图片、固定头和未来少量元数据；六个物理记录合计 `0xF0000`，可放入独立的 `0x100000` 数据分区。
- 增加该分区后仍保留约 3.70 MiB 未分配 Flash，不挤占 3 MiB 应用分区、工牌资料、NVS 或 `cardid`。
- 运行时只显示一个槽位。继续使用 mmap + LVGL 图片描述符后，三张图片不会同时复制到 RAM，因此 3 槽不会引入约 450 KiB 的堆需求。

**结论：当前硬件和分区空间足以可靠支持 3 个个性化图片槽位，不需要退化为 2 个或 1 个。**

## 可复用能力与差距

| 能力 | 可复用实现 | 当前差距 | 初步决策 |
| --- | --- | --- | --- |
| 事务存储 | `badge_record` / `badge_store` / `badge_partition` 的双副本、CRC、提交标记 | 数据尺寸和三逻辑槽模型不同 | 复用事务模式，新建独立 `custom_data` 记录与 store，不修改工牌 schema |
| 零拷贝显示 | 工牌 mmap 像素 + `lv_image_dsc_t` | 个性化为 240×320、多槽切换 | 映射独立分区，视图仅绑定当前有效槽位 |
| 模式可用性 | `mode_t::is_available` | `has_content` 未接持久化状态 | 由“至少一个有效槽位”驱动可用性 |
| 本地按键 | 活动模式 `handle_key` | 个性化尚无处理器 | 短按上/下循环有效图片；全局长按语义保持不变 |
| Wi-Fi/HTTP 生命周期 | token、Busy、分块上传、更新事件 | HTTP 仅认识工牌 store | 在同一热点会话增加独立个性化 API 和更新事件 |
| Web 图片处理 | 解码、拖动、缩放、旋转、RGB565 编解码 | 当前只支持 200×200 和工牌形状 | 泛化为指定宽高的 cover 裁剪；个性化固定 240×320、3:4 |
| 配置页面 | 已有工牌表单和状态反馈 | 没有配置类别和槽位选择 | 保留工牌表单行为，新增清晰独立的个性化配置区 |

## 关键约束

- Phase 0～3 只修改本规格目录；需求、设计和任务拆解确认前不得修改生产代码、分区表或测试代码。
- 必须保留 `badge_data@0x310000/0x40000`、`cardid@0x356000/0x4000`、NVS 和 3 MiB 应用分区；不得要求全片擦除。
- 个性化固定输出 240×320 RGB565 LE，实现屏幕像素 1:1；不在设备端引入 JPEG/PNG 解码器。
- 每个逻辑槽位独立事务更新。写入失败只能影响目标槽位的未提交副本，不能损坏该槽位上一版本、其他个性化槽或工牌资料。
- HTTP 继续按块接收，不在 ESP32 堆上保存完整 153,600 字节请求体或额外图片副本。
- LVGL 对象一次创建并复用；Flash 映射和图片缓存切换必须保证旧指针生命周期、缓存失效和锁边界正确。
- 工牌配置 API、字段、默认入口和保存行为保持兼容；新增 UI 不得把两个表单的图片或提交状态串联。
- 自动化只能证明记录、协议、状态机和构建基线；LCD 像素、实体按键、手机触控及断电恢复必须单独真机验收。

## 主要风险

- 分区表新增条目本身不会擦除后续数据，但错误地址或普通上传范围配置可能威胁 `cardid`；实现前后必须脚本化校验所有边界。
- 240×320 图片比工牌照片大 92%，Flash 擦除/写入和 HTTP 传输耗时更长，需要维持上传超时、Busy 状态和断连回退的正确性。
- 三槽各自双副本会在启动时验证多份 CRC；需要测量启动耗时，避免为扫描全部记录造成明显黑屏。
- LVGL 若在切换槽位后继续缓存旧描述符，可能显示旧图或访问无效地址；视图需在换源前显式丢弃对应缓存。
- 将现有方形裁剪函数泛化为矩形时容易回归工牌 200×200 的缩放、拖动和圆形/圆角输出，必须保留旧 Web 用例并增加矩形用例。
- 手机浏览器同时持有原图、Canvas RGBA 和 RGB565 body 时会占用数百 KiB 到数 MiB 内存；应避免为三个槽位同时解码三张原图。
