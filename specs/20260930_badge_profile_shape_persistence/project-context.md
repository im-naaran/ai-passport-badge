# 项目上下文

> 状态：已确认

## 当前工程

- 本仓库是 ESP32-C3 展示固件，使用 PlatformIO、ESP-IDF 5.5.3、LVGL 9 和内嵌离线网页。
- 工牌资料保存在 `badge_data@0x310000/0x40000`，由两个 `0x20000` 槽位事务轮换；普通升级不得擦除该分区、NVS、`custom_data` 或 `cardid@0x356000/0x4000`。
- 工牌图片固定为 200×200 RGB565 LE、80,000 字节。RGB565 没有 Alpha，网页上传时会把透明遮罩外像素合成到设备背景色 `#0B0F0E`。
- 当前工作区包含尚未提交的三槽个性化功能及相关整理，后续实现必须保留这些改动，不执行暂存、提交或破坏性 Git 操作。

## 当前形状链路

- 网页已经提供 `square`、`rounded`、`circle` 三个互斥选项，并通过 `BadgeImage.renderCrop()` 对最终 Canvas 像素裁剪。
- `rgbaToRgb565()` 会把透明像素合成到设备背景色，因此圆角和圆形外围以近黑色实像素写入 Flash；设备显示正确，但像素本身不再含透明信息。
- `GET /api/photo` 返回保存后的 RGB565；`rgb565ToImageData()` 将所有像素恢复为不透明。重新进入网页时，当前代码固定把形状初始化为 `square`，所以已保存圆形/圆角照片的近黑色外围会显露。
- 用户手动重新选择原形状时，现有 Canvas 裁剪已经可以隐藏外围；缺失能力是形状的持久化、API 返回和自动选中。

## 当前记录与协议

- Flash 支持工牌记录 schema 1（姓名、图片）和 schema 2（姓名、bio、图片），记录头固定 40 字节，包含元数据、payload CRC、header CRC 和最终提交标记。
- HTTP 上传兼容 envelope version 1 和 version 2。version 2 使用 14 字节头，携带姓名长度、bio 长度和固定图片长度，图片继续按块写入，不缓存完整请求体。
- `badge_profile_snapshot_t`、`badge_upload_meta_t` 和 `GET /api/profile` 当前没有照片形状字段。
- 单个工牌槽位仍有充足空间把记录头从 40 字节扩展到 44 字节并容纳形状元数据，无需调整分区或槽位大小。

## 可复用能力与差距

| 能力 | 可复用部分 | 当前差距 |
| --- | --- | --- |
| Flash 事务 | 双槽、CRC、读回校验、最后提交 | schema 1/2 没有形状 |
| HTTP 流式上传 | version 分派、定长校验、分块图片写入 | envelope 1/2 没有形状 |
| 工牌查询 | `/api/profile` 与 `/api/photo` 分离 | profile JSON 不返回形状 |
| Web 编辑 | 三种形状、Canvas 裁剪、已有照片反显 | 初始化固定方形，未恢复形状 |
| 兼容测试 | 旧 schema、旧 envelope、事务失败覆盖 | 缺少 schema/envelope 新版本及形状恢复用例 |

## 关键约束

- 不改变工牌图片尺寸、RGB565 格式、分区地址、槽位大小或双槽事务语义。
- 不为设备端新增完整图片副本，也不把裁剪移动到 LVGL；设备继续显示已经烘焙完成的 RGB565。
- 项目仍处于开发阶段，用户已明确不要求兼容 schema 1/2 或 envelope version 1/2；升级后旧记录可回退到默认工牌，旧请求可直接拒绝。
- 旧分区内容不得被启动流程自动擦除；只是不再解释为有效工牌，首次新版保存再按现有双槽事务覆盖非活动槽。
- 圆形或圆角图片已经丢失遮罩外原始像素；形状扩大时无法恢复角落，网页必须明确这一不可逆边界。
- 自动化测试与真机证据继续分开记录；构建不能代替 Safari、Chrome、LCD 和重启恢复验收。

## 主要风险

- schema 3 payload 偏移计算错误可能导致新图片起点错位或 CRC 失败。
- envelope v3 若未同步最大长度和任意分块解析，可能出现截断或越界。
- 只恢复 radio 而不重新按形状裁剪反显 Canvas，仍会显示已烘焙的近黑外围。
- 用户从圆形切回方形时若没有警告，会误以为系统能恢复已丢失的原图角落。
